## 1. 产品定位

### 1.1 它回答的问题

用户搜一个楼盘，落到决策报告页，应当在首屏内得到一句结论 + 支撑维度，并能回答：

1. **这个盘值不值得我放进候选？** → 一句话结论（值得入候选 / 值得比较 / 谨慎比较）
2. **它强在哪、弱在哪？** → 盈利 / 地段 / 退出 / 租赁 四维评分（满分 10）
3. **它对「我」合不合适、我买得起吗？** → 接 calculator v2 的购买力 + ABSD/身份负担，做成与四维同级的「适配度」（见 §4.1.6）
4. **附近有没有更好的替代？** → 同区/同价位的近似盘对比

### 1.2 它不做的事

- ❌ **不做房源列表/中介挂盘聚合**——我们不是 PropertyGuru，搜的是「项目（project）」不是「房源（listing）」
- ❌ **不替用户下买/不买的硬判断**——结论只到「值得入候选 / 谨慎比较」这种**相对**措辞，不说「别买」「强烈推荐」
- ❌ **不出具估价数字**——不做 AVM，不说「这套值 S$X」；价格只呈现「近 12 月成交 PSF 区间 × 面积的算术换算」，且明确标注非估价（见 §11）
- ❌ **不在数据不足时假装精确**——分数估算来源必须显式标注（见 §4.3）
- ❌ **不做地图找房（map-search）**——地图只作单盘的证据伴随，不是搜索主入口（与主 PRD 非目标一致）

### 1.3 产品基调

**结论先行，但结论是「相对的」、可解释的、带置信度的。**

twohomes 值得抄的核心：先给一句人话结论（Worth shortlisting），再用四个分数支撑，每个分数数据不够就老实说「这是从相似盘估的，谨慎看」。这和 calculator v2 的「让数字说话、不家长式干预」一致——我们给力度（一句结论 + 分数），但把判断权和不确定性都摊开给用户。

### 1.4 与现有模块的关系

| 模块                          | 关系                                                                           |
| ----------------------------- | ------------------------------------------------------------------------------ |
| **Calculator V2**（购买力）   | 决策报告页的「适配度」复用其购买力区间 + ABSD/身份负担，无需重算                |
| **Module 4 深度报告**（人工） | 本功能是它的**自动化、单盘、即时版**；深度报告升级为 3-5 盘人工精修             |
| **Module 5 对比器**           | 「附近替代」tab 只做**候选发现与跳转**；**所有跨盘「A 比 B 好」结论统一由对比器产出**，本功能不出对比结论 |
| **Quiz**（买家画像）          | 用画像给结论措辞做轻量个性化（学区型优先看 Location 维度）                      |
| **Lead OS**                   | 搜索/查看楼盘是高意向信号，进 journey events，喂 lead 评分；数据反馈也进其队列  |

## 2. 用户流程

```
搜索入口（首页 / 工具页 / 文章内嵌 / 计算器结果页）
  ↓
输入楼盘名（自动补全）/ 或选区+价位浏览
  ↓
搜索结果（项目卡片列表，带核心分数预览）
  ↓
点进单盘 → 决策报告页
  ├─ 决策快照（结论 + 四维 + 适配度 + 关键指标）   ← 首屏决策层
  ├─ 四维评分详情（可展开看子因子 + 解释）
  ├─ 详情 Tab（成交 / 租赁 / 地段 / 学校 / 替代 / 户型 / 价格）
  └─ 伴随地图（随 tab 切换证据图层，移动端默认折叠懒加载）
  ↓
转化 CTA（保存 / 对比 / 要深度报告 / 约顾问）
```

**无需登录即可搜索 + 看完整决策报告。** 登录只 gate 在「保存 / 要深度报告 / 约顾问 / 价格提醒」（与 calculator v2 一致）。

## 3. 搜索入口与结果

### 3.1 搜索框

- 单输入框 + 自动补全（楼盘名为主，支持区 / 街道 / 邮编模糊）
- 数据源：`projects` 表（URA 缓存，见 §6）
- 空查询时给「热门楼盘」「按区浏览」两个引导
- **零结果兜底**：不报错，给「这个盘我们还没收录，要不要按区找近似的？」+ 留资入口；并埋 `condo_search_zero_result`（驱动收录优先级，见 §8.2）
- **冷启动期（`projects` 未铺满）**：搜索只露「按区浏览 / 留资」，**绝不展示空列表或半截数据**（见 §6.3）

### 3.2 搜索结果列表

项目卡片（移动端单列，桌面 2-3 列），每张卡片显示：

| 字段             | 说明                                                |
| ---------------- | --------------------------------------------------- |
| 楼盘名 + 区      | 例：The Gazania · D19                                |
| 一句话结论徽章   | 值得入候选 / 值得比较 / 谨慎比较（颜色编码）         |
| **盈利分**（主） | 0-10，最显眼；数据不足显示「相似盘估算」角标         |
| PSF 区间         | 近 12 个月成交 PSF range（非估价，见 §11）           |
| 关键标签         | 产权（永久/99年）· TOP 年份 · 总户数 · 最近 MRT 步行 |
| 适配度提示       | 若已做 calculator：「在你预算内 / 略超」绿/橙点      |

- 排序：默认按盈利分降序；可切「PSF 低→高」「TOP 新→旧」
- 每张卡片右上角：收藏 ♥ + 加入对比 ⊕（最多 4 个）

## 4. 决策报告页（核心）

URL：`/condo/{slug}`（可分享，OG 卡片带结论 + 盈利分）。slug 生成规则见 §6.2。

### 4.1 Block 1 · 决策快照（Decision Snapshot）

页面第一屏，**结论先行**。包含：

1. **标题**：`{楼盘名} · 一眼看懂`
2. **结论徽章**（三档，软措辞）：
   - 🟢 值得入候选（Worth shortlisting）
   - 🟡 值得比较（Worth comparing）
   - 🟠 谨慎比较（Compare carefully）
3. **一句话总结**：由四维拼成自然语言（模板拼装，非 LLM，见 §6-文案），例：
   > 盈利记录不错但算不上突出，值得比一比。地段不错，最近地铁约 6 分钟。退出风险可控。租赁需求健康。
4. **决策评分图**（雷达 / 四宫格），四维同屏，分档 Strong / Mixed / Caution / Missing
5. **关键指标条**：已 TOP · 产权 · 最近 MRT（X 分钟）· 总户数
6. **适配度（与四维同级）**：把 calculator 的购买力从「叠加条」提升为显著模块——
   - 「这个盘当前 PSF 下约 S$X.XXM 起；你的舒适区间 S$X.XX–X.XXM」
   - 叠加身份负担：「你作为 PR 买第二套，ABSD 约 30%（≈ S$XXX,XXX）」——直接复用 `lib/tax`
   - 没做过计算器则显示「测一下买不买得起 →」
7. **信任条**：数据源 = URA · 最后计算时间 · 分数版本（见 §5.4）· 「发现数据有误？反馈」

> 设计红线：快照里的每个分数、每句结论，都必须能点开看「怎么算的」（§4.3）。不允许出现无法解释的黑箱分。

### 4.2 Block 2 · 四维评分体系

每维满分 10，分档：**优秀 ≥7 / 良好 ≥5 / 一般 ≥3 / 偏弱 <3 / 数据不足 N/A**。

| 维度                | 衡量什么                            | 子因子（可展开）                                | MVP 状态        |
| ------------------- | ----------------------------------- | ----------------------------------------------- | --------------- |
| **盈利分** Profit   | 近年转售价格涨幅 vs 市场基准        | 按户型拆分；交易太少标「不计入」                | ✅ 完整算       |
| **地段分** Location | 地铁通达 + 名校距离 + 周边配套      | 最近 MRT 步行分钟、1km 内小学、配套密度         | ✅ 完整算       |
| **退出分** Exit     | 未来转售/退出的难易                 | 供应宽松度 + HDB 升级客需求（**不复用盈利分**） | 🔜 灰显「即将上线」 |
| **租赁分** Rental   | 租金回报 + 出租率 + 跨户型收益一致性 | 毛租金回报率、出租单位占比、收益方差            | 🔜 灰显「即将上线」 |

> **MVP 口径统一**：退出 / 租赁两维在 MVP **灰显占位 + 标「即将上线」**，雷达图上以浅色呈现，**不参与结论徽章计算**，结论只由盈利 + 地段 + 适配度得出。避免 §1.1 与 §9 口径打架。

每个维度卡片包含：分数 + 档位文案 + 一句话解释 + 「怎么算的？」展开 + 「发现错误？反馈」。

**市场状态标签**（给盈利/退出维度加语境，带 tooltip）：

- 流动活跃 Liquid & Active / 惜售 Tightly Held / 冷清 Thin Market / 高换手低需求 Churny
- 盈利特例：短期冲高 Short-Term Spike / 历史薄弱 Thin-History / 自开盘跑输 Weak Since Launch / 新盘 New Project

### 4.3 数据诚实度（设计红线，必须实现）

twohomes 最值得抄的不是分数，是**它对数据不足的诚实**。强制规则：

| 触发条件                          | 标注                                       | 可测断言（见 §13）                         |
| --------------------------------- | ------------------------------------------ | ------------------------------------------ |
| 本盘近 12 月转售 < 3 笔           | 「数据覆盖低，分数可靠性下降」             | 响应 `confidence != "high"` 且 UI 出现文案 |
| 本盘转售历史不足，用邻近相似盘估  | 「从相似盘估算」+ 显示用了几个盘           | `confidence == "estimated_similar"`        |
| 只有 1-2 个相似盘                 | 「仅 1-2 个相似盘估算，当方向性信号看」    | `basis.similarProjects.length <= 2`        |
| TOP 不足 1 年                     | 「新盘，分数会随数据增加变化」             | `regime == "new_project"`                  |
| 某户型交易太少                    | 「该户型交易不足，不计入评分」             | 户型行标 `excluded`                        |
| 完全无转售历史                    | 盈利分显示 N/A，不硬凑                     | `score == null`                            |

### 4.4 Block 3 · 详情 Tab 区

Tab 顺序（移动端可横滑，桌面横排）：

| Tab        | 内容                                                          |
| ---------- | ------------------------------------------------------------ |
| 概览       | 楼盘档案（地址/产权/TOP/户数/开发商）+ 决策快照锚点          |
| 成交       | 历史成交表 + PSF 走势图（URA），可按户型筛                   |
| 租赁       | 租金估算、毛回报率、出租率                                   |
| 地段       | 地图 + 最近 MRT/巴士、步行分钟、配套清单                     |
| 学校       | 1km / 2km 内小学，排名、报名历史（若有）                     |
| 替代       | 同区/同价位近似盘卡片 →（仅入口）一键进对比器（Module 5）    |
| 户型/平面  | 户型分布、面积、site plan（有则放）                          |
| 价格       | 当前 PSF 区间、首付/月供（接 calculator）                    |
| 相册       | 项目图片（有则放）                                            |

### 4.5 Block 4 · 伴随地图（Map Companion）

- 右侧（桌面）/ 可折叠（移动）的地图，**随 tab 切换图层**：
  - 概览（周边楼盘分数点）→ 交通（MRT/出口/巴士/单车道）→ 配套 → 学校 → 成交语境 → 附近替代 → 附近 HDB 升级需求 → 未来供应
- **性能约束**：移动端地图**默认折叠、懒加载、点击才初始化地图库**；首屏只渲染决策快照，保证 LCP（见 §13）
- MVP 可只做：概览 + 交通 + 学校 三层；其余 Phase 2

### 4.6 Block 5 · 转化 CTA 卡

- 主：**「要这个盘的深度报告（免费）」** → 触发 Module 4 人工深度报告流（Layer 2 留资）
- 次：「和另一个盘对比」→ Module 5 对比器
- 次：「约 15 分钟顾问」→ Module 8
- 轻量：收藏 ♥（gate 登录）+ 「降价/新成交提醒」开关

## 5. 评分引擎逻辑（工程参考）

> 所有分数**确定性**（同数据快照同输出）、**可解释**（返回子因子明细）、**带置信度**。

### 5.1 输出结构（建议）

```ts
interface ProjectScore {
  dimension: "profit" | "location" | "exit" | "rental";
  score: number | null;          // 0-10，null = 数据不足
  band: "excellent" | "good" | "fair" | "poor" | "insufficient";
  confidence: "high" | "low" | "estimated_similar";  // 驱动 §4.3 标注
  components: Record<string, number>; // 子因子明细，供「怎么算的」展开
  regime?: MarketRegime;         // 市场状态标签
  basis?: { similarProjects?: string[]; txnCount?: number };
  snapshotDate: string;          // 数据快照日期（见 §5.4）
  scoreVersion: string;          // 算法版本（见 §5.4）
}
```

> `band` 的英文枚举与 §4.2 中文档位（优秀/良好/一般/偏弱/数据不足）必须**单一来源定义**（一处常量映射），避免两套口径漂移。

### 5.2 各维度算法骨架

- **盈利**（MVP）：本盘近 N 年同户型转售价 CAGR vs 同区基准；样本不足回退到相似盘（按区+价位+TOP 年龄聚类），并置 `confidence = estimated_similar`
- **地段**（MVP）：OneMap 算最近 MRT 步行时间 + 1km 小学数 + 配套密度，归一化加权
- **退出**（V2.1）：供应宽松度（未来供应/存量）+ HDB 升级需求（周边 HDB resale 成交，data.gov.sg）。**移除「转售需求用盈利分代理」**，避免与盈利维度共线
- **租赁**（V2.1）：毛回报率（租金 PSF / 售价 PSF）+ 出租率 + 跨户型方差
- **一句话结论**：四维分档 → 模板拼装（见 §6），非 LLM 自由发挥（避免幻觉数字）

### 5.3 复用现有代码（已核对实际代码）

> ⚠️ 楼盘多维评分是**全新模块**，建议新建 `lib/project-scoring/`。**不要**扩展 `lib/scoring/`——那是 lead 评分 stub（输出 `hot/warm/cool/cold`、7 个固定加权项），与楼盘 0-10 多维评分无关。

可如实复用的：

| 现有代码                                              | 用途                                              |
| ----------------------------------------------------- | ------------------------------------------------- |
| `lib/calculator/v2-compute.ts` → `computeV2`          | 适配度的购买力区间、首付/月供                     |
| `lib/tax/` → `calculateAbsd` / `calculateBsd` / `solveMaxPurchasePrice` | 适配度的 ABSD/身份负担、PSF→可负担总价反推 |
| `lib/finance/rent-estimate.ts` → `estimateMedianRent` | 租赁维度的租金基准                                |
| `lib/finance/index.ts` → `regionalAppreciationLookup` | 盈利维度的同区基准回退                            |

### 5.4 分数版本化与漂移解释

输入（URA 成交、相似盘集合）每晚都在变，用户收藏后回看分数会变（主 PRD §4.2 returning user）。不解释直接伤信任——这是本产品的核心卖点。

- `project_scores` 表存 `data_snapshot_date` + `score_version`（见 §6.1）
- 报告页「最后计算时间」旁给 diff 文案：「较上次 +0.3，因新增 4 笔成交」
- 算法迭代时 bump `score_version`，历史快照保留可回溯

## 6. 数据底座与冷启动

> **现状（已核对）**：`projects` 表当前仅 `external_ref / name / district / tenure / top_year / total_units / developer / metadata`，**无 slug、无经纬度、无 PSF**；`project_transactions` / `project_amenities` 只画在主 PRD §16.1 ER 图，**migration 尚未建**。MVP 盈利/地段分缺数据底座——本节补齐。

### 6.1 表结构改动

**`projects` 扩展列**：

| 列                | 类型        | 说明                          |
| ----------------- | ----------- | ----------------------------- |
| `slug`            | varchar UNIQUE | URL 用，生成规则见 §6.2     |
| `lat` / `lng`     | numeric     | OneMap geocode，地段维度用    |
| `psf_min` / `psf_max` | numeric | 近 12 月成交 PSF 区间（缓存） |
| `psf_period_end`  | date        | PSF 区间数据截止日            |
| `status`          | enum        | active / hidden / stub        |

**新建表**：

- `project_transactions`（成交，盈利/PSF 来源）：project_id、txn_date、price、area_sqft、psf、bedroom_type、sale_type
- `project_amenities`（地段来源）：project_id、kind(mrt/school/mall/…)、name、distance_m、walk_minutes
- `project_scores`（评分缓存）：project_id、dimension、score、band、confidence、components(jsonb)、regime、basis(jsonb)、`data_snapshot_date`、`score_version`、computed_at
- `project_data_feedback`（数据纠错，见 §7.2）

### 6.2 slug 生成规则

- 项目名 → 小写、去空格/特殊符 → 英文盘名直接用；同名加区后缀（`the-gazania-d19`）
- 唯一约束在 `projects.slug`；冲突时追加短哈希
- 历史 slug 变更需 301（SEO，见 §10）

### 6.3 冷启动策略

- **MVP 先人工 seed 50–100 个热门盘**（与主 PRD §10.5「30 个 pre-cached」、§21 对齐）
- URA / OneMap 批量缓存管线作为独立 Sprint 任务，夜间增量刷新 `project_transactions` / `project_amenities` / `project_scores`
- `projects` 未铺满时：搜索框只露「按区浏览 / 留资」，**不展示空列表**（§3.1）
- 未收录盘被搜：`status=stub` 占位 + 留资，不渲染半截报告

### 6.4 数据源

| 源              | 用途                          | 备注                                    |
| --------------- | ----------------------------- | --------------------------------------- |
| **URA REST API**| 成交、项目档案、PSF 历史      | 免费需注册；夜间批量缓存                 |
| **OneMap API**  | MRT/巴士/学校/配套、步行时间、geocode | 政府免费                        |
| **MOE**         | 小学详情、P1 报名历史         | 半公开                                  |
| **data.gov.sg** | HDB resale 成交（退出维度）   | 免费                                    |
| 人工            | Master Plan、未来供应、en-bloc| 判断类，喂退出维度                      |

> 待定（同 calculator v2 开放问题）：URA 刷新频率、相似盘聚类阈值、租金数据覆盖度。

### 6.5 容量与成本规划

> 数据库是最贵的线上资源，但**这套缓存表本质很小**——新加坡私宅市场就这么大（约 2,500–3,000 个非有地私宅盘、买卖成交 ~2 万笔/年、租赁合约 ~9–10 万份/年）。

**估算（行宽含索引）：**

| 表                              | MVP（50–100 盘） | 全量（~3000 盘）        | 说明                       |
| ------------------------------- | ---------------- | ----------------------- | -------------------------- |
| `projects`                      | <1 MB            | ~6 MB（3,000 行）       | 档案，几乎不变             |
| `project_transactions`（买卖）  | ~7 MB            | ~45 MB（留 10 年 ~20 万行）| 盈利分/PSF 来源          |
| `project_transactions`（租赁）  | ~10 MB           | ~43 MB（留 24 月 ~19 万行）| **行数最多**，只需近 1–2 年 |
| `project_amenities`             | ~1 MB            | ~12 MB（~12 万行）      | MRT/学校/配套，静态        |
| `project_scores`（最新）        | <1 MB            | ~6 MB（3000×4 行）      | jsonb components           |
| **合计（稳态）**                | **~30 MB**       | **~150–200 MB**         | 免费档 500 MB 即可容纳     |

**两条强制剪枝规则（防悄悄膨胀）：**

1. **`project_scores` 历史 change-only**：每晚给 3000 盘 ×4 维写历史 = ~440 万行/年。**只在分数变化时写新行**（无新成交不写），历史按月保留。否则小表会被撑成大表。
2. **租赁表设 TTL**：租金回报只需近 12–24 个月，定期删旧行，别留十年。

**成本认知**：线上 DB 贵在**计算/连接数/IOPS**，不在 GB 存储。本设计的夜间缓存恰恰省钱——用户访问只读本地索引表（低 IOPS），不在请求路径上调外部 API；热门盘被反复看也是查同一份缓存、零额外成本。真正吃 DB 写入的是主 PRD 的 `lead_journey_events`（高频写），不属于本功能这几张缓存表。

## 11. 合规与免责

> 主 PRD §18.3 把合规列为一等公民，并指出平台定位为「信息匹配而非 estate agency advisory work，上线前需律师确认」。本功能把「打分 + 下结论 + PSF 区间」往前推了一大步，**法律边界必须先界定**。

- **法律定性**：决策报告为「基于公开数据的方法论参考」，**非估价、非投资建议、非 CEA 监管下的物业咨询**
- **强制免责条款**：报告页底部常驻——
  > 本页分数与结论由公开数据（URA / OneMap / MOE / data.gov.sg）按既定方法论计算，仅供参考，不构成估价、投资建议或受 CEA 监管的物业咨询。请在决策前咨询持牌专业人士。
- **措辞红线**：价格一律表述为「近 12 月成交 PSF 区间的算术换算」，禁用「估值 / 这套值 / valuation」
- **律师 review 范围**（Phase 0）：显式纳入「楼盘打分 + 结论徽章 + PSF 区间」三项，以及 Schema.org 评分标记的合规性
